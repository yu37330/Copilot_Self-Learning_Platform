# WikiのOKF v0.2対応（Issue #23）

## 変更前の問題

PR #22のWM（AgentCore Memory型）/WO（独自原本型）は共通のMarkdownを出力するが、YAML frontmatterと必須の`type`がなく、OKFではなかった。出典・ハッシュ・未承認状態は独自JSONにしかまとまっていなかった。

## 改修内容

両方式の`export_wiki()`は、標準でOKF v0.2のWikiバンドルを生成する。LLM生成・AWS通信は行わず、検査済みの既存revisionを同じレンダラーで表現する。

```text
wiki-bundle/
  index.md                 # ルートだけokf_versionを宣言
  python-env.md            # type: Reference / status: draft / sources
  references/src-....json  # 実際に引用した抜粋と出典メタデータ
  wiki.json                # 既存の主張・適用条件・根拠・版情報を保持
  manifest.json            # Markdown・出典JSON・索引を含む全ファイルのSHA
```

概念ページは`type/title/description/status/generated/sources`を持つ。各主張に、`sources[].id`へ対応する安定IDの脚注を付ける。IDは出典IDのUTF-8 hexから作り、Windowsの大文字小文字差でも衝突しない。`sources[].resource`は実在する同梱引用抜粋JSONを指す。架空のS3 URLは生成しない。引用抜粋は原本全文ではなく、原本文書のSHAと抜粋ファイルのSHAを区別する。

`generated.by`は書式生成処理を示す`process:copilot-wiki-okf-1`。元のLLMや本人を推定しない。元revisionに生成日時がないため、`generated.at`と`log.md`は生成しない（いずれも任意）。前版ハッシュは`wiki.json`と拡張メタデータに保持する。

**すべて`status: draft`。`verified`は付与しない。** ハッシュ・引用の存在・OKF構造検査は、主張が正しいこと、社内承認、署名済み本人性を意味しない。`x_copilot_learning`に元の方式・候補の出所・版ハッシュと未承認フラグを残す。WMの`derived_memory`とWOの`raw_document`は区別し、Memory由来の文章を原本の検証済み証拠と偽装しない。

## 必須依存関係

```powershell
python -m pip install -r requirements-okf.txt
```

PyYAMLはOKF frontmatterの安全な解釈と構造検査に使う。パッケージ取得は会社の許可済み経路・ミラーを使用する。その他のAWS停止ゲートは変更しない。Python 3.10以降を想定し、今回の動作確認はLinux/Python 3.13.5/PyYAML 6.0.3で行う。Windows実機は別検証。

## 両方式のデモ

```powershell
python .\scripts\demo_wiki_offline.py --out "$env:USERPROFILE\okf-wiki-demo-01"
python .\scripts\validate_okf_offline.py --directory "$env:USERPROFILE\okf-wiki-demo-01\original"
python .\scripts\validate_okf_offline.py --directory "$env:USERPROFILE\okf-wiki-demo-01\agentcore"
```

必ずGit管理外の新規フォルダへ出力する。デモの候補は合成・手作りであり、実LLMの生成結果ではない。既存`wiki_offline.py build`の新規出力もOKFへ変わる。

## 旧形式の移行

旧形式も`verify`で検証できる（`format: legacy`）。旧版を上書きせず、独立保管したmanifest SHAと現在の原本で検証し、別フォルダへ移行する。

```powershell
python .\scripts\wiki_offline.py migrate-okf `
  --mode original --input "<元の入力JSON>" --input-sha256 "<入力の正規化JSON SHA>" `
  --training-sha256 "<元の訓練SHA>" --project "<元のproject>" `
  --policy "<Git外の機密辞書>" --directory "<旧版Wikiフォルダ>" `
  --manifest-sha256 "<旧版の独立保管SHA>" --out "<新規OKFフォルダ>"
```

WMは`--mode agentcore`と元のMemory入力JSONを使う。`wiki.json`の知識revision・parent SHA・採否は変えず、表現形式だけを移行する。出力manifest SHAは変わるので、新しい値を独立保管する。原本変更、ページ改変、同一/配下の出力先は拒否する。旧ページIDが`index`/`log`の場合はOKF予約名と衝突するので、勝手に改名せず候補ページIDとリンクの修正を求める。

## 形式検査と安全性検査は別

`validate_okf_offline.py`は読取専用の構造検査。成功0、不適合1、入力/依存関係エラー2。レポートの書き出しは`--out <Git外・検査対象外の新規JSON>`を指定する。

- 概念ページのparse可能なYAML frontmatterと空でない文字列`type`を検査。
- `index.md`を置く場合は見出し構造、frontmatterはルートの`okf_version`だけ。`log.md`を置く場合はISO日付・新しい順のグループを検査。
- 任意項目・indexの欠落、未知のtype/キー、壊れたリンクは形式不適合にしない。壊れたリンクは警告。一人の`verified`mappingはリストへ正規化するが、自動承認しない。
- 安全なYAMLプロファイルとして、実行型タグ、重複キー、alias参照、過剰な深さ・件数・容量を拒否。これはOKFそのものの必須項目とは別のローカル安全制限。
- 一般的なOKF構造検査は出典の意味・本文の安全性を認定しない。第三者のOKFを自動でKnowledgeStoreへ取り込む機能ではない。
- 既存アプリのWiki生成/verifyは、出典・機密検査・リンク・ファイル構成まで引き続き厳密に照合する。一般のOKFで許されることと、このアプリで採用できることを区別する。

## ファイルと検証

`copilot_learning/okf.py`、`copilot_learning/wiki.py`、`scripts/wiki_offline.py`、`scripts/validate_okf_offline.py`、`tests/test_okf.py`、`requirements-okf.txt`。

回帰対象はWM/WOの出力・再検証、frontmatter注入、出典脚注、Memory provenance、引用抜粋、大小文字ID、旧版検証/移行、改変・余分なファイル・リンク・途中失敗、任意メタデータ・未知type/キー・壊れたリンクの許容。テスト件数はPRに今回の実行値を記録する。CI/GitHub Actionsは使わない。

## 範囲・制約

生成Wikiの交換形式が対象。リポジトリ内のREADME等すべてをOKF概念へ変えるものではなく、Copilot用SKILL.preview.mdの書式も別物のまま。実LLM編集・AWS接続・SSO/DLP・Skill配布・実性能比較は未接続/未検証のまま。OKF形式にしただけでAgentRun同等の学習品質になったとは判断しない。
